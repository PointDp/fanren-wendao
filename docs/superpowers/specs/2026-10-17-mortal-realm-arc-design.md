## 一、意图与缘起

v1 交付了引擎 + 第一章《测灵》（炼气二层封顶，约 9200 字）。用户确认扩容：**最少写完人界篇**——主角从炼气一路修到**化神**，化神即人界顶点，之后人界再无进阶之路，必须**自己想办法飞升离界，否则老死于此**。设定框架参考《凡人修仙传》（人界/灵界之分、大境界瓶颈、灵气枯竭、寿元压迫），故事与人物仍为原创凡人流。

## 二、目标

1. 剧情从第一章无缝续写至人界终点：炼气 → 筑基 → 结丹 → 元婴 → 化神 → 终局抉择
2. 每个大境界突破都是**玩法化的剧情抉择**：准备（道具/因果/人脉/灵石）决定成败，失败有真实代价（重伤、退境、寿元折损），不引入随机数
3. 化神后进入**大限倒计时**压迫结构：寿元只减不增，倒逼玩家在有限时间内寻找飞升之法
4. 多结局：老死（专属盖棺定论）/ 飞升离界（人界篇正结局）/ 坐化传道（无奈但温情的第三选择）
5. 第一章的因果、好感、道具、旗标全部承接并在后文兑现（残页、大比、张铁、李师姐、王管事、执法堂旧案）

## 三、非目标

- 灵界篇不写（飞升即人界篇终，结局留白）
- 不做战斗数值小游戏（维持"文字叙事+选择"）
- 不做二周目（数据结构已留口子）
- 不改存档格式 saveVersion（向后兼容）

## 四、机制扩展（引擎侧改动清单，保持最小）

### 4.1 境界表扩容（realm.js）

`FC.REALMS` 追加（**只追加，不改既有索引**，旧存档自然兼容）：

```
索引 0-12：凡人、炼气一~九层、筑基一~三层（不变）
13-15：结丹一层、结丹二层、结丹三层
16-18：元婴一层、元婴二层、元婴三层
19：化神
```

共 20 级。`FC.REALM_TIERS` 新增分界表：`{炼气:0, 筑基:10, 结丹:13, 元婴:16, 化神:19}`，供剧情与状态栏判断大境界。

### 4.2 寿元曲线（state.js advanceDays 不动，境界提升时加寿）

大境界突破时按"入阶加寿"一次性增加（写进各章效果里，不进引擎）：

| 境界 | 入阶加寿 | 参考寿元上限 |
|---|---|---|
| 筑基（每层） | +40 年（已有） | ~200 年 |
| 结丹（每层） | +80 年 | ~450 年 |
| 元婴（每层） | +150 年 | ~900 年 |
| 化神 | +300 年 | ~1200 年 |

凡人流关键体验：**寿元的绝对值在涨，但相对下一道瓶颈永远不够**。回乡探亲、故人老死等桥段由各章剧情承担。

### 4.3 大境界突破（纯内容实现，引擎不改）

突破 = `choice`/`hub` 节点 + `show/enabled` 条件（修为顶层 + 机缘道具/因果齐备）+ 分支：

- **准备充分** → `{type:'res',key:'cultivation',delta:N}` + 寿元效果 + 好结局文案
- **准备不足硬闯** → `{type:'death',cause:'兵解'}` 或重伤（injury +X）+ **退境**（cultivation -1）
- **缓一缓** → 留在瓶颈，继续攒机缘（hub 循环）

第一章已验证此模式（柴房夜练）。各章突破条件在设计到计划时逐章定死。

### 4.4 大限倒计时（终章机制，state.js 微扩）

进入化神时置 `flags.mortal_limit=true`。终章通过既有 `time` 效果推进时间、`lifespanYears` 自然递减（`lifespanYears` 到 0 即死亡 `dead='lifespan'`，已有逻辑）。**不需要新增倒计时系统**——压迫感直接来自寿元数字。唯一引擎改动：`deathText`（ui.js）增加"老死（寿终）"已存在，补充"飞升离界/坐化传道"两个**非死亡结局**的展示：终章以 `terminal` 节点 + 全屏结局文呈现（引擎已有 terminal 支持，无需改）。

### 4.5 存档兼容

- REALMS 追加式扩容 → 旧存档 `cultivation:1|2` 语义不变
- 新章内容以新文件（js/content/ch2.js…）注册进 `FC.Content`，graph 合并注册
- `saveVersion` 保持 1

## 五、分篇结构（7 个内容包 + 1 个系统包）

字数目标合计 12-15 万字（含分支）。每包独立可玩、独立存档检查点。

### 系统包（先做）：《筑基之上》
- REALMS 扩表 + REALM_TIERS、状态栏显示大境界色（纯文字标记，如【结丹】）
- deathText 补充兵解/丹毒文案分档
- 存档槽位不变；`~` 面板境界跳转支持新表
- 回归：第一章全流程测试保持绿

### 第二章《外门大比》（约 1.5-2 万字，炼气三→七层）
- 主线：开春大比。伪灵根正面斗法必败——三条夺名路径：**苦功流**（提前用残页对照引气诀，knows_truth 线奖励：功法勘误）、**人情流**（张铁/李师姐线好感达标获得助力）、**险棋流**（揭发对手作弊，动用执法堂旧案 knows_truth 因果）
- 关键抉择：大比名次 vs 结仇内门弟子；救场张铁 vs 保名次
- 好感线：李师姐筑基在即，赠别或同门之谊
- 收尾：前十记名弟子，授《引气诀》全本，脱杂役籍；残页与全本对照发现残页多出半句"气起于踵"——大机缘伏笔
- 章末瓶颈：炼气七层，卡在"炼气后期需灵药固本"，引出第三章

### 第三章《筑基》（约 2-2.5 万字，炼气七→筑基一~二）
- 主线：宗门十年一度发放筑基丹，名额一个。伪灵根需**三枚**才有把握——机缘三选一：替宗门剿矿盗（危险、正道）、随商队走黑市（灵石与人情、灰色）、入深山采筑基草（九死一生、但遇奇遇残页共鸣"气起于踵"）
- **回乡探亲**高光段：离家十余年，父母坟头草高（寿元主题第一次重击；时间快进体验）
- 突破抉择：一枚丹硬闯（重伤退境风险）、三枚丹稳（耗时数年、寿元流逝）、残页辅助（knows_truth/残页齐备 → 水到渠成）
- 张铁线分岔：他先筑基（走商队起家）或留守青牛镇老死（好感与因果决定哪条）
- 章末：筑基成功寿元 +40，宗门授予内门功法《青元剑诀》，但宗门上空魔气隐现——大战将至

### 第四章《结丹》（约 2-2.5 万字，筑基二→结丹一~二）
- 主线：魔道入侵，宗门倾覆。撤离/死战/护送凡人三条路线（承接因果：当年顶过罪的人此刻舍命报恩——karma 兑现的高光）
- 李师姐线收束：她结丹失败兵解，遗言托付（好感线情感重锤）；或她结丹成功远走，临别赠物
- 流亡岁月：散修身份，坊市、佣斗、夺宝；结丹需**金丹机缘**（地火淬体/前辈洞府/丹药三条路）
- 突破抉择：结丹失败=丹毒入体（寿元 -20 + injury 50）或兵解
- 章末：结丹成，寿元 +80；得知人界灵气枯竭的传闻初现

### 第五章《元婴》（约 2.5-3 万字，结丹二→元婴一~二）
- 主线：散修岁月高光。元婴老怪博弈（骗、借势、螳螂捕蝉），原创反派"枯荣老祖"（元婴后期，觊觎主角机缘）
- **闭关百年**：快进玩法高光——一键百年，出关时坊市易主、故人皆亡（凡人流最重的时移世易体验）
- 元婴瓶颈：需**婴变契机**（心魔劫以剧情抉择呈现：直面当年执法堂旧案/顶罪真相/张铁之死的执念）
- 突破抉择：强冲（心魔反噬 death 风险）vs 了结尘缘因果（knows_truth/好感线清账 → 稳）
- 章末：元婴成，寿元 +150；枯荣老祖逼夺机缘，最终对决（境界/准备/因果三重条件决定胜负，败=兵解）

### 第六章《化神》（约 2.5-3 万字，元婴二→化神）
- 主线：人界灵气枯竭真相揭开（上古大战打碎界膜，灵气外泄）——化神是**天地允许的最后一阶**
- 化神之机：上古化神修士陨落遗迹"通天遗府"，机缘与杀局并存；残页"气起于踵"在此兑现（半句口诀是遗府钥匙之一）
- 化神突破：人界首例千年无成；抉择（集齐三钥/借枯荣老祖遗泽/以自身寿元燃寿硬闯——燃寿=寿元 -200 的豪赌）
- 章末：化神成，寿元 +300，天地异象，**大限钟声**：人界再无下一步

### 终章《大限》（约 1.5-2 万字，化神，倒计时结构）
- 主线：寿元只减不增（快进即燃烧生命）。三线索寻飞升：**上古飞升台**（需集齐三件遗宝）、**界膜薄弱点**（需元婴以上修为硬撼，重伤风险）、**传承 newer 大能残留神念**（对话式抉择，揭人界篇主题：仙路尽头是什么）
- 结局分支（全为 terminal 节点 + 专属结局文）：
  1. **老死**：寿元归零，专属盖棺定论文（按生平因果生成段落：顶过罪的人、救过的人、留下的名字）
  2. **飞升离界**：集齐条件破界而去——人界篇正结局，留白灵界
  3. **坐化传道**：自愿放弃飞升，散尽功力于天下灵根少年，温情悲剧结局
- 结局后回标题界面，保留"重新开始"（二周目留待将来）

## 六、非目标与红线

- 不写灵界；不写韩立原著人物与具体桥段（只借设定框架）
- 不引入随机数（一切成败由 state 条件决定）
- 不改存档格式；不破坏 file:// 零依赖约束
- 每个内容包交付时全量测试必须绿（既有 131 例不回归）

## 七、留给计划阶段的裁定点

- 各章节点图的具体节点数与 hub 循环次数——写作时定，validate 兜底
- 死亡结局文案的分档细则（兵解/丹毒/妖口/寿终/战死已有四档，扩到六档）
- 面板"章节跳转"随新章自动扩展（meta.chapter 注册机制，沿用 checkpointNode 模式）
